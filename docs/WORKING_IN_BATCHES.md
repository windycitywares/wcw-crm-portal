# Working in batches (small PRs)

Owner's rule, same as the shop: **work in batches and open small PRs** — never the whole milestone in one shot.

1. One batch = one focused PR (one layer or feature area, ideally < ~1,500 changed lines).
2. Every PR is green in CI and safe to deploy on its own.
3. Commit and push early; open the PR as soon as the batch is done.
4. Base on `main` when possible; if a batch needs the previous one, say "Depends on #N" and merge in order.
5. After each PR: a short status to the owner, then the next batch.
6. Keep the plan below current so a new session can pick up the next batch.

Branch `feat/<area>-<n>-<short-name>` · PR title `<Area> <n>/<total>: <what it does>`.

v1 ends at M7. SPEC §3.9 puts the unified inbox first after it, and §9 decision 3 makes "the inbox phase" the
last thing the shop's own inbox and campaigns wait on. The design follows the CRM's existing habit: **a
conversation is a ticket** (the shop's contact form already opens one, M3 batch 5), so the inbox is channels
arriving into tickets — one place to work with SLA, assignment and permissions already in it — not a second
conversation store next to the first one.

Two notes for whoever picks this up:

- The M8 branches were cut one from the next on top of the campaign follow-up branches, so the
  stack is `main` → `fix/campaign-tracking-links` → `feat/m5-6-one-click-unsubscribe` → batch 1 → batch 2
  → batch 3 → batch 4 → batch 5 → batch 6. Merge order follows from that: the campaign fix first, then one-click
  unsubscribe, then M8 1 → 2 → 3 → 4 → 5 → 6 (each PR states its dependency). Rebasing M8 onto `main` to make
  the PRs independent is possible but needs a force-push, so it is the owner's call.
- Batch 1's migration is `0024` off `0022_suppliers`, batch 2's is `0025` off `0024`, batch 3's is `0026`
  off `0025` and batch 5's is `0027` off `0026` (batches 4 and 6 add no table), so each says "depends on" the
  one before and they merge in order. The unmerged
  `feat/m6-2-supplier-products` carries `0023`; whichever of *those* merges second must repoint its
  `down_revision` — the usual branch refresh does it (merge `origin/main` in, keep both sides).
- Mail and the channels share one set of filing rules (`filing.py`) on purpose: a second implementation would
  drift, and a chat message that filed differently from a letter is a bug nobody would notice. What batch 6
  does *not* do: a sender known only by phone (an SMS carries no address, and a customer is found by address
  today, so such a message is filed unlinked for staff to link by hand), and the connectors themselves —
  those are on the sending side.
- One SMTP identity still sends: replies go out through Admin → Settings → Email as they do today, even for a
  message that arrived on a mailbox. Sending *from* the mailbox it arrived on needs per-account SMTP
  credentials and is a follow-up, not a silent assumption. Outbound attachments ride along with that
  follow-up: today the CRM keeps what the customer sends and the reply is plain text through that one
  identity, so a file attached to a reply would not leave the building.

## CI repair (2026-10-18)

`backend.yml`'s DB suite had not passed since M3 batch 1 (#27) — about 70 red runs — so everything merged since was
never executed. Two PRs put it green: **#69** fixed the one compile-time break that stopped the suite running at
all; **#70** then repaired the product and the tests the run exposed.

| # | Item | Contents | PR |
|---|------|----------|----|
| 1 | Python 3.11 compile | `SettingsService.get_model()` used PEP 695 generic syntax (`def get_model[T]`), which the CI/server interpreter (3.11) cannot parse — the suite died at the compile step before a single test ran. Local Python was newer and accepted it | #69 |
| 2 | Real bugs the suite reached | `updated_at` is written by the database (`onupdate=func.now()`), so an update path that built its response from the in-memory object lazily loaded it after `commit()` and raised `MissingGreenlet` (500): deal items, SLA policies, canned responses, supplier contacts and products now `refresh()` after commit, the pattern tags/lookups/notes already used. A customer created with `marketing_consent=false` was wrongly stamped `unsubscribed_at` (only true → false is an unsubscribe). Converting a lead passed `stage_id=None` explicitly and lost the default pipeline's first stage. A downloaded attachment gained `; charset=utf-8` on a `text/*` type. Audit `changes` for a campaign's `scheduled_at` (a datetime) and a supplied product's money columns (Decimals) were not JSON, so scheduling and product edits 500'd. **And `record_event` never committed, so every open pixel and every click was rolled back — the tracking report read 0 in production** | #70 |
| 3 | Stale tests | the inbox test patched the file-size limit on the old `poller` module instead of `filing`; campaign helpers tagged customers as `marketing`, which may only *view* them (SPEC §2), so they now tag as an admin; a per-class name counter so helper names stop repeating between tests; the unsubscribe-token regex dropped the `:` the token is built from; `<p>`-derived text keeps its blank line; supplier-type tests pick the first *active* value; the shop suite sets up the SLA the API seed adds in production; `follow_redirects` (the httpx spelling); the tracking tests pass a token, not the whole URL the builder returns; a `tags` rule takes ids; "spent at most 20" includes a customer who never ordered (spend defaults to 0); the dashboard stats assert a floor; and `setUp` ends any campaign a test left mid-flight, because the dispatcher works over the whole database | #70 |

Result: **264 tests, OK (2 skipped)** — the first green DB run since 2026-10-17. CI and the server run Python 3.11;
a syntax the local interpreter accepts can still fail there, so prefer 3.11-compatible code.
